# 视频评审台使用手册

视频评审台把一条广告视频的生产拆成四道关卡：**G1 创意 → G2 分镜 → G3 资产 → G4 成片**。每道关卡都先查红线，再按维度打 1–5 分。评审器用 deepseek-flash 读文字、看图、看成片关键帧；成片的响度、黑场、冻结帧、分辨率等技术指标由程序测量，不交给模型猜。

站点有三个用途：

- **在线评审**：上传材料，1–3 分钟拿到带证据的评审报告。
- **查标准**：评审框架和评分标准与评审器使用的是同一份 `rubrics.json`。
- **看评审器靠不靠谱**：420 个带标准答案的构造用例，所有评测结果和评审理由都能逐条查看。

## 快速开始

1. 打开 **在线评审**，选择关卡。
2. 上传或粘贴待评审材料，并附上**前序关卡已通过的材料**作为参考（见下表）。缺少参考材料时，“还原度”类维度只能凭空判断，分数会偏中间。
3. 采样次数保持默认 3 次。提交后会跳到结果页，页面自动刷新，可以关掉稍后在 **评审记录** 里查看。

表单里已经填好一份分镜示例（测试集 S03 在线英语 App），直接点“开始评审”就能看到完整报告。

### 每道关卡提交什么

| 关卡 | 待评审材料 | 参考材料 | 备注 |
|---|---|---|---|
| G1 创意 | 创意提案（文字） | brief、品牌规范 | 提案里写清目标人群、核心洞察、故事线、CTA |
| G2 分镜 | 分镜表（文字，可附草图） | 已通过的创意提案 | 每个镜头写明时长、景别、运镜、画面、台词/字幕、音效 |
| G3 资产 | 主视觉、角色设定、落版等图片 + 资产清单 | 分镜表 + 品牌规范 | 资产清单里写明字体、音乐、肖像的授权情况，评审器据此判断授权红线 |
| G4 成片 | 成片视频一个（≤150MB） | 分镜表 | 台词和字幕请贴到“台词/字幕”框；投放平台不是抖音竖屏时填写平台规格 |

### 文件格式

- 文字：`.md`、`.txt`、`.csv`、`.srt`，也可以直接粘贴。
- 图片：`.png`、`.jpg`、`.webp`。图片原样发送给模型，同时附上程序测得的分辨率。
- 视频：`.mp4`、`.mov`、`.webm`。程序抽取前 3 秒每 0.5 秒一帧、其余均匀 12 帧和片尾一帧，统一缩放到 768 宽。
- 单次提交的文件合计不超过 150MB。

## 怎么读评审报告

报告从上到下依次是：结论 → 优先修改 → 技术参数（仅成片）→ 红线检查 → 维度评分。

### 结论是怎么算出来的

模型只给证据和分数，结论由程序按规则计算：

| 结论 | 条件 |
|---|---|
| 驳回（命中红线） | 任意一条红线在多数采样中命中 |
| 通过 | 加权总分 ≥ 4.0，且所有维度 ≥ 3 分 |
| 修改后通过 | 加权总分 ≥ 3.0，且所有维度 ≥ 2 分 |
| 驳回 | 其余情况 |

### 红线的三种状态

- **命中**：多数采样都判定命中，直接驳回。
- **疑似（需人审）**：只有少数采样判定命中。不自动驳回，但报告顶部会提示人工复核。
- **未命中**。

### 什么时候必须人工复核

报告顶部出现“需人工复核”时，说明以下两种情况至少出现一种：

- 同一维度在 3 次采样中分差 ≥ 2 分，模型自己拿不准。
- 有红线处于“疑似”状态。

此外，下面这些情况评审器**看不到**，无论报告怎么写都需要人看：

- **声音**：模型听不到音频。配乐是否卡点、口播是否清晰、BGM 是否侵权，只能靠程序测出的响度数值加上人耳判断。
- **连续运动**：模型只看关键帧。AI 视频常见的闪烁、穿模、手指崩坏、运动不连贯，帧与帧之间的问题可能漏掉。
- **图片上的小字**：主视觉上产品名的单字错误（如“轻氧”写成“青氧”）识别不稳定，见基准测试结果。
- **授权真伪**：评审器只能根据资产清单的描述判断授权，无法核验合同。

### 维度详情

展开每个维度可以看到：

- 评分标准，以及 5 分和 2 分各自的锚点描述。
- 模型引用的**证据**，如具体镜头、时间码或字幕原文。
- 指出的问题和可执行的修改建议。

建议先看证据是否属实，再看分数。证据错了，分数就不可信。

## 推荐的评审流程

1. **机审先行**：每份材料先过评审器，命中红线的直接退回修改，不占用人工评审时间。
2. **人审把关**：以下三类必须人审：
   - 结论为“通过”或“修改后通过”、准备进入下一关的材料；
   - 报告提示“需人工复核”的；
   - 成片的声音和运动部分。
3. **抽检校准**：每周从机审结果中抽 ≥ 20% 交人工复评，记录分歧。分歧集中在某个维度时，修改该维度的评分标准描述。
4. **合规终审**：广告法、AI 生成内容标识、投放平台审核规则以法务和平台最终意见为准。评审器的红线检查用来提前发现问题，不替代合规审核。

## 评审器靠不靠谱：基准测试

目前没有人工标注的历史样本，所以采用**构造法**建立标准答案：先写合格的基准样本，再用程序往里注入一个已知缺陷。注入了什么，标准答案就是什么。

### 数据集

- 8 个行业：饮料、美妆、在线教育、汽车、手游、金融理财（B 站横屏）、母婴、消费电子。每个行业都有完整的创意、分镜、资产和成片。
- 共 420 个用例，分四类：

| 类型 | 做法 | 标准答案 |
|---|---|---|
| 基准 | 人工撰写的合格样本，程序自动检查不含极限词 | 不应命中红线 |
| 红线 | 注入极限词、功效断言、未授权 IP、危险行为、AI 标识缺失、黑场/冻结、授权缺失等 | 应命中指定红线 |
| 质量缺陷 | 注入单一缺陷，如 Logo 开场、无 CTA、越轴、响度过低、错别字 | 对应维度比基准降 ≥ 1 分 |
| 不变性 | 只改格式、打乱顺序或追加无信息的空话 | 总分变化 ≤ 0.3 |

- **开发集** S01–S02 用来调评分标准；**测试集** S03–S08 只用来出报告，不根据它修改标准，避免过拟合。
- 资产图和成片是程序生成的低保真示意稿：文字卡片加底色、字幕和噪点。它们只用于检验评审器能否发现注入的缺陷，**绝对分数不代表真实画质**。

### 指标

| 指标 | 含义 | 目标 |
|---|---|---|
| 红线召回 | 注入红线的用例中，评审器命中该红线的比例 | ≥ 90% |
| 误报率 | 未注入红线的用例中，评审器判定命中任一红线的比例 | ≤ 10% |
| 缺陷灵敏度 | 注入质量缺陷后，目标维度比基准下降 ≥ 1 分的比例 | ≥ 80% |
| 不变性 | 只改格式时，总分变化 ≤ 0.3 的比例 | ≥ 90% |
| 非目标维度 \|Δ\| | 注入一个缺陷时，其他维度的连带变化 | 越小越好 |

### 怎么使用基准测试页面

- **基准测试** 页面按关卡列出指标，颜色表示是否达标：绿色达标，黄色接近，红色差距较大。
- **用例库** 里筛选“未通过”，可以逐条看到评审器判错的用例，以及它的完整理由。
- 修改评分标准后，在开发集上重跑并对比，确认没有变差，再跑测试集。

### 构造法的局限

构造标签只能证明评审器**能发现已知缺陷**，不能证明它的分数和专家一致。构造的缺陷也比真实缺陷更“干净”，所以测试集成绩应视为评审器能力的上限估计。要确认与专家的一致性，见下一节的人工校准。

## 人工校准

1. 导出待标注表。每个关卡按类型分层抽 12 例，共 48 例，顺序已打乱，也不显示变体类型：

   ```bash
   cd benchmark
   ../.venv/bin/python human_agreement.py export --n 12
   ```

2. 请 2 位以上评审专家打开 `benchmark/annotation/待标注_<关卡>.csv`，对照用例库里的材料逐维度打分，并填写命中的红线和结论。
3. 计算一致性：

   ```bash
   ../.venv/bin/python human_agreement.py agree --run test_v1
   ```

4. 达标线：维度分数二次加权 κ ≥ 0.6，±1 分一致率 ≥ 85%。达不到的维度，说明评分标准的描述或锚点不够清楚，需要修改后在开发集上重新验证。

## 命令行用法

其他系统接入请用 HTTP 接口，见“接口文档”页面。在服务器上也可以直接用命令行评审，适合批量处理：

```bash
# 在仓库根目录执行
# 分镜评审，附创意提案作参考
.venv/bin/python video_review.py storyboard 分镜.md --context 创意.md
# 资产评审
.venv/bin/python video_review.py asset KV.png 角色.png 资产清单.md --context 分镜.md 品牌规范.md
# 成片评审
.venv/bin/python video_review.py video final.mp4 --context 分镜.md --transcript 字幕.srt \
  --platform-hint "B站横屏 16:9 1920x1080，-16 LUFS"
```

常用参数：

- `--runs`：采样次数，默认 3。
- `--effort`：推理强度，可选 low / high / max。
- `--out`：报告输出目录，默认 `reports/`。

每次评审输出一份 Markdown 报告和一份 JSON 结果。

基准测试相关命令：

```bash
cd benchmark
../.venv/bin/python build_dataset.py                                # 重新生成数据集（约 25 分钟）
../.venv/bin/python run_benchmark.py --name dev_v4 --split dev      # 开发集
../.venv/bin/python run_benchmark.py --name test_v2 --split test    # 测试集
../.venv/bin/python run_benchmark.py --name test_v2 --split test --score-only   # 只重算指标
```

评测结果缓存在 `results/<轮次名>/`，中断后用同样的命令重跑，会跳过已完成的用例。站点的基准测试页面自动读取所有带 `summary.json` 的轮次。

## 费用与耗时

- 单次采样输入约 0.15–1.5 万 token（成片含关键帧图片最多），输出约 0.4–0.8 万 token，耗时 40–90 秒。默认 3 次采样并发执行。
- 实测：开发集 61 个用例、每例采样 1 次，花费约 ¥1.9。在线评审默认 3 次采样，每份材料约 ¥0.1。
- 账户余额不足或 API Key 失效时，任务会立即失败，并提示“API 鉴权或余额问题”。

## 部署与运维

从零部署的完整流程见仓库根目录的 `部署文档.md`。以下路径均相对仓库根目录。

| 项目 | 位置 |
|---|---|
| 站点代码 | `review-site/`（Next.js 15） |
| 评审器 | `video_review.py` |
| 评分标准 | `rubrics.json`（站点和评审器共用，修改后无需重启） |
| API Key | 仓库根目录 `.env` 中的 `DEEPSEEK_API_KEY` |
| 站点密码 | `review-site/.env.local` 中的 `SITE_PASSWORD` |
| 在线评审任务 | `review-site/data/jobs/<任务号>/`（输入文件、结果 JSON、Markdown 报告、日志） |
| 运行日志 | `review-site/data/server.log` |

常用操作：

```bash
cd review-site
./serve.sh restart    # 重启（改了代码要先 npm run build）
./serve.sh stop
./serve.sh status
```

- **更换 API Key**：修改 `.env` 即可，下一个任务自动生效。
- **修改密码**：修改 `.env.local` 后执行 `./serve.sh restart`。
- **并发**：服务器只有 1G 内存，同一时间最多跑 2 个评审任务，其余排队。可通过环境变量 `MAX_RUNNING` 调整。
- **服务重启**：正在运行的任务会标记为失败，需要重新提交。
- **更新分享快照**：跑完新的评测轮次后，执行 `node scripts/snapshot.mjs <输出.html> <在线版地址>` 重新生成只读快照，再发布到 claude.ai。

## 常见问题

**分数普遍在 3 分左右，是不是评审器不敢打高分？**
LLM 评审有趋中倾向。评分标准为每个维度写了 5 分和 2 分的锚点，并要求先写证据再打分，以此缓解。判断时应更看重维度之间的相对高低，以及证据指出的具体问题。

**同一份材料评两次，结论不一样？**
默认 3 次采样取均值，红线按多数票判定，就是为了减少这种波动。仍然出现分歧时，报告会提示人工复核。基准测试中，资产关卡对图片顺序比较敏感，总分波动在 0.35–0.55 之间。

**能评真实拍摄或 AI 生成的成片吗？**
可以。基准测试里的成片都是示意稿，所以真实成片上的绝对分数还没有经过校准。建议先拿 10–20 条已经有投放结论的真实视频，对比评审器的结论，再决定是否作为正式流程。

**评审器能替代平台审核吗？**
不能。它用来在提交平台审核之前，提前发现广告法极限词、功效断言、AI 标识缺失等常见问题，减少被驳回的次数。最终以平台审核和法务意见为准。
